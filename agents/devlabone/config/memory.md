# DevLabOne Persistent Memory & Context Skill

The **Memory Skill** defines the persistent context management, state tracking, and architectural decision logging protocols for the **DevLabOne** AI agent system. It ensures that DevLabOne retains project knowledge, architectural choices, and execution state across IDE sessions and multi-step tasks.

---

## 1. Memory Architecture & Storage Layers

DevLabOne uses a two-tier memory architecture to separate project-specific execution state from global agent rules:

```
                                [ DevLabOne Agent ]
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
   [ Layer 1: Project Memory ]                      [ Layer 2: Workspace Memory ]
  (projects/<project>/.devlabone/)                  (agents/devlabone/config/memory.md)
  ├── context.json                                  ├── System Standards & Conventions
  ├── adr_log.md                                    ├── Global Architectural Guidelines
  └── execution_history.json                        └── Reusable Design & Stack Rules
```

### Layer 1: Project-Specific Memory (`projects/<project-name>/.devlabone/`)
Every project generated or maintained within `projects/<project-name>/` maintains a dedicated `.devlabone/` directory containing persistent runtime state:

- **`context.json`**: Machine-readable state metadata including active tech stack, framework versions, database engine, engaged orchestrators, and open feature modules.
- **`adr_log.md`**: Human-readable Architecture Decision Records generated by the **Solution Architect** (`skills/solution-architect.md`).
- **`execution_history.json`**: Changelogs, bug fix records, refactoring logs, and test coverage metrics.

### Layer 2: Workspace & Repository Memory (`agents/devlabone/config/memory.md`)
Global memory stored in repository config defining overall standards, coding rules, preferred library defaults, and agent operational constraints.

---

## 2. Pre-Execution Context Verification Protocol

Before DevLabOne performs any greenfield generation, feature enhancement, refactoring, or bug correction, it must execute the following 4-step memory verification flow:

### Step 1: Memory Discovery
Check for the existence of `projects/<project-name>/.devlabone/context.json`.
- If present: Load project memory into active session context.
- If absent: Initialize `.devlabone/` directory and create default `context.json` during intake.

### Step 2: ADR & Architectural Rule Inspection
Read `projects/<project-name>/.devlabone/adr_log.md` to verify previous architectural decisions (e.g., chosen database ORM, state management strategy, authentication flow).

### Step 3: Domain Orchestrator Alignment
Pass the recalled context state to the **Solution Architect** (`skills/solution-architect.md`) and downstream domain orchestrators (`frontend-orchestrator`, `backend-orchestrator`, `database-orchestrator`, etc.) to prevent conflicting tech stack decisions.

### Step 4: Post-Execution State Commit
Upon completion of work, update `context.json`, record new ADRs in `adr_log.md`, and append execution summaries to `execution_history.json`.

### Architecture Decision Record (ADR) Log Format (`adr_log.md`)
```markdown
# Architecture Decision Records (ADRs) - [Project Name]

## ADR-001: Selection of Primary Database Engine
- **Date**: YYYY-MM-DD
- **Status**: Accepted
- **Context**: Project requires ACID compliance, relational queries, and complex joins for financial analytics.
- **Decision**: Selected PostgreSQL 16 managed via Prisma ORM.
- **Consequences**: Enables strict type safety, clean migrations, and strong transaction consistency.

## ADR-002: Authentication & Authorization Strategy
- **Date**: YYYY-MM-DD
- **Status**: Accepted
- **Context**: Need secure multi-tenant user authentication with RBAC.
- **Decision**: Implemented JWT access tokens with secure HTTP-only refresh tokens.
- **Consequences**: Stateless backend verification; requires redis blacklisting for immediate token revocation.
```

## 4. Integration with DevLabOne 10-Step Master Protocol

The Memory Skill hooks directly into the 10-Step Master Protocol defined in `devlabone.md`:

| Protocol Step | Memory Skill Action |
| :--- | :--- |
| **Step 1: Request Intake** | Check for `projects/<project-name>/.devlabone/context.json` & initialize memory if missing. |
| **Step 2: Solution Architect Engagement** | Read `adr_log.md` to ground architectural decisions in past choices. |
| **Step 3–9: Orchestrator Execution** | Enforce tech stack rules defined in `context.json` across Frontend, Backend, Database, Security, and DevOps. |
| **Step 10: Final Verification & Handover** | Write updated execution metadata, log new ADRs, and update `context.json` in `projects/<project-name>/.devlabone/`. |
